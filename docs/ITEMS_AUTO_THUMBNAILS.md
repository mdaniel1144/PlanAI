# Automatic Item thumbnails

[Dimension verification and display units](ITEMS_DIMENSIONS_HARDENING.md) adds persisted source/ADMIN verification and actual rendered-size proof to the dimension-confirmation prerequisite described here.

## Audit and implementation plan

The existing `model-cache.ts` loads authenticated GLBs, owns a bounded cache, clones editable materials per instance, and awaits appearance textures. `ModelPreview.ItemModel` supplies the workspace transform: bottom-center anchor, one uniform metres-per-unit scale, and confirmed Y orientation. Catalog grids fetch image assets only. Images already have secure immutable storage and Sharp decoding; `item_assets.inspection_json` is available for generated-image provenance without a migration. The editor and catalog use local React state rather than a query-cache library.

Plan: share the existing transform and appearance code; add a dedicated deterministic browser renderer and tested camera fitter; register generated bytes through an ADMIN-only endpoint with source fingerprint and previous-image checks; replace the manual thumbnail step with an automatic Product image panel; exercise real rendering, regeneration, cache isolation, validation, and rollback.

Pre-change SQLite backup: `/tmp/habitat-before-auto-thumbnails.sqlite`. Read-only inspection found the live Item is now ACTIVE with saved dimensions and a manual cover. Those values are preserved. Unconfirmed legacy/draft dimensions still will not be guessed or filled in.

## Thumbnail Renderer

`generateItemThumbnail()` creates a separate Three.js scene and off-DOM canvas. It loads the same cached GLB, clones instance materials, applies the default appearance, applies the shared model transform, updates world bounds, waits for shader compilation, renders, and exports. No visible-page screenshot, UI, controls, selection highlighting, grid, labels, or debug geometry enters the scene. No server renderer or new rendering dependency is added.

## Camera

`fitCameraToObject()` uses the eight calibrated world-bounds corners. A perspective camera with 42° vertical field of view looks toward the bounds center from the normalized `(4, 3, 5)` direction: +X/+Z, slightly above the product. Each projected corner determines the required horizontal/vertical distance, with 15% padding. Near/far planes scale with object size. The fit does not depend on a prior user orbit or a fixed distance.

## Lighting

Every image uses an opaque `#eeeee8` background, white ambient light at intensity 2, a white key at `(4, 8, 5)` with intensity 3, and a white fill at `(-4, 3, -2)` with intensity 0.6. No dramatic ground shadow or random environment is used.

## Orientation / Calibration

`modelTransform()` is shared with `ItemModel`, used by the catalog preview and workspace. It centers the original X/Z bounds, puts the original minimum Y at zero, then applies confirmed Y orientation and one scalar `metresPerModelUnit`. There is no axis stretching. Server readiness must confirm canonical real dimensions before generation is eligible; an old technical calibration alone is insufficient.

## Default Color

The renderer selects the current ACTIVE default color and calls the existing `applyVariant()` implementation. Original GLB appearance is used before a default color exists. The same binding, material, texture-channel, UV, and color rules apply to capture and previews. Required textures are awaited explicitly before rendering; no arbitrary capture timeout is used.

## Image Output

512 × 512 physical pixels at pixel ratio 1, WebP quality 0.9, with browser PNG fallback accepted. The renderer explicitly uses sRGB output, ACES filmic tone mapping, and exposure 1, matching the preview's display pipeline. Images remain compact catalog assets.

## Storage

`POST /api/admin/items/:itemId/generated-thumbnail` saves bytes as a THUMBNAIL asset and atomically updates `items.thumbnail_asset_id`. No image bytes enter SQLite. Existing `inspection_json` stores `source: GENERATED_FROM_GLB`, canonical model ID, nullable default color ID, source signature, and decoded 512 × 512 dimensions; the asset already stores Item ID and creation time. GLB inspection remains separate in the API projection. No migration is needed.

Regeneration always creates a new immutable ID and storage key. The previous generated asset is removed only after a replacement is committed and only if no Item or color still references it. Referenced generated images and manual covers are retained. Private authenticated asset delivery remains unchanged.

## Regeneration

The server computes a SHA-256 fingerprint from renderer convention version, canonical model ID/hash, calibration, real dimensions, anchor convention, active default color ID/overrides, canonical mappings, and the default color's material/texture definitions. It excludes names, descriptions, brands, categories, SKU, price, status, unrelated colors, and unrelated materials.

The open admin editor automatically generates after calibration, on reload with a missing/outdated generated image, and after render-affecting changes. Model replacement waits for its required dimension confirmation. The Product image panel offers Regenerate thumbnail and Try again. The primary wizard has no manual image-upload step. The old manual asset endpoint remains compatible for future custom-cover tooling.

Generation runs in an authenticated admin browser. Changes made through an API without an open editor are marked outdated and are generated when an admin opens the product; user catalog grids never perform generation.

## Failure Safety

Uploads supply the expected render fingerprint and prior cover ID. Both are checked inside the registration transaction, so an old render or concurrent replacement cannot overwrite newer state. Invalid images, stale renders, storage errors, and failed attachment leave the prior image intact. New files are compensated on transaction failure; obsolete-file cleanup occurs after commit and can recover on startup.

UI cancellation suppresses stale results when the Item changes or the editor unmounts. Failure shows “Thumbnail could not be generated from the 3D model.” with Try again; technical detail is folded under Advanced. Existing valid thumbnails continue to satisfy publication readiness during a failed regeneration.

If another admin changes the default appearance during capture, a stale upload causes the editor to reload authoritative source data and generate the new appearance. It never retries the obsolete source indefinitely.

## Performance

Only the admin Product image module imports the renderer on demand. Generation reuses the bounded authenticated GLB/texture caches and their ownership leases. Temporary cloned materials are released in `finally`; the dedicated renderer is disposed and its WebGL context released. Shared cached geometry and textures are not disposed by capture.

New asset IDs prevent stale image bytes. The editor receives fresh Item data after registration. Catalog mounts, focus, same-tab update events, and cross-tab storage events refresh catalog data. Generated Item covers take precedence over legacy per-color card images. Catalog grids still request thumbnail images only.

## Security

Registration requires ADMIN authentication and the existing mutation/CSRF header. Request bytes are bounded; only PNG/WebP uploads are accepted. Sharp verifies actual format, full decode, one image, resolution limits, and exactly 512 × 512 dimensions. The server derives source IDs and metadata from the requested Item rather than trusting client-supplied provenance. Same-Item references, model validity, dimension confirmation, and stale-image checks remain server-authoritative. USER uploads are forbidden.
